OrderHub · MCP server lifecycle

A local MCP server: build → live → triggered → changed

Your OrderHub.Mcp is not a library you link — it's a small executable server process that Claude Code launches on demand and talks to over pipes. Here's exactly how it turns from source into a running tool, and what it takes for a service-layer edit to reach the agent.

What the project actually is

The csproj says <OutputType>Exe</OutputType> — a runnable console program. The service layer is the library; the MCP references and links it in, then runs as its own OS process that speaks MCP on stdin/stdout.

01

Build — dotnet build

Compilation drops the server and its own copy of every dependency into one output folder. It does not share DLLs with the web app — it carries its own OrderHub.Core.dll and OrderHub.Infrastructure.dll.

The service layer is baked in as a copy. Whatever version of OrderHub.Core.dll sits in this folder is what the server will run — that's why a rebuild is the thing that moves new rules into place (Stage 04).
02

Deploy — there is no server to deploy to

With stdio transport (what we use), the MCP has no port, no host, no cloud. The bin/ folder is the deliverable. Claude Code just launches that program when it needs it.

◆ Local · stdio  (this project)

  • Artifact = the compiled bin/ folder on disk
  • Started as a child process, lives only during a session
  • "Redeploy" = simply restart the process
  • Needs its own DB connection string

◇ Remote · HTTP  (the other option)

  • A long-running service you host somewhere
  • Reached over the network by many clients
  • A code change means an explicit rebuild + redeploy
  • Reuses the API's auth instead of raw DB access
03

Register & trigger — how it comes online

training-repo/.mcp.json doesn't hold code or tools. It holds one thing: the name and the exact command to spawn the process.

{ "mcpServers": {
the registry Claude Code reads on start
"orderhub": {
↳ the server's name → shows in /mcp
"command": "dotnet",
what to run…
"args": ["run", "--project", "src/OrderHub.Mcp"]
↳ build-then-run this project as a child process
} } }
CLAUDE CODE · client
OrderHub.Mcp · server process
  1. 1
    ▶ Spawn the process
    Open Claude Code in the folder → it reads .mcp.json → runs the command as a child, wired to its stdin/stdout.
    $ dotnet run --project src/OrderHub.Mcp (incremental build, then start)
  2. 2
    → initialize  ← serverInfo
    The MCP handshake over the pipes. The server announces itself.
  3. 3
    → tools/list  ← [ get_order, low_stock, … ]
    Now the tools appear in /mcp. This is "online."
  4. 4
    ⏸ Idle & alive
    The process stays running, waiting on stdin, for the whole session.
  5. 5
    → tools/call low_stock {threshold:5}
    The agent decides to use a tool; the request goes down the pipe.
    ↳ server runs C# → OrderService → EF Core → SQL Server
    ← content: [ {"Sku":"SKU-1048","StockQuantity":2}, … ]
  6. 6
    ■ Session ends
    Claude Code kills the child process. No daemon is left running — it lives and dies with the session.
04

How a code change reaches the agent

Because .mcp.json runs dotnet run (build-then-start), every spawn rebuilds first — so a fresh start picks up edits to the service layer automatically. But a process already running is frozen on the DLLs it started with.

You edited the service layer, then…Runs new code?Why
Start a new Claude Code session (or reconnect the server in /mcp)yesdotnet run rebuilds on spawn → new OrderHub.Core.dll is loaded fresh.
Nothing — keep the same live sessionnoThe child process is still running the old DLLs in memory. No hot-reload. Restart it.
Config pointed at a prebuilt DLL instead of dotnet runnoRuns whatever was last built — stale until you rebuild yourself. (That's why we chose dotnet run.)
// the whole rule in one line edit rules → restart the server → next spawn does dotnet run = rebuild → agent now runs the new logic
!
First spawn after a change is slower (it's compiling), and a short client timeout can miss it. Run dotnet build once before launching Claude Code so the on-spawn build is a no-op and the server connects instantly.
TL;DR — build → the bin folder is the artifact → Claude Code spawns it per session & talks over stdio → restart to pick up new code.

OrderHub · MCP 伺服器生命週期

一支本機 MCP 伺服器：建置 → 上線 → 被觸發 → 變更

你的 OrderHub.Mcp 不是被你連結進去的函式庫——它是一支由 Claude Code 按需啟動的可執行伺服器程序，透過管線（pipe）與它溝通。以下說明它如何從原始碼變成執行中的工具，以及一次 service 層的修改要怎樣才能真正傳到 agent。

00

這個專案到底是什麼

csproj 裡寫的是 <OutputType>Exe</OutputType>——一支可執行的 console 程式。service 層才是函式庫；MCP 把它參照並連結進來，然後以自己的 OS 程序執行，透過 stdin/stdout 說 MCP 協定。

01

建置 — dotnet build

編譯會把伺服器連同它自己的每一個相依 DLL一起放進單一輸出資料夾。它不與網站共用 DLL——它帶著自己的一份 OrderHub.Core.dll 與 OrderHub.Infrastructure.dll。

# 於 training-repo/ dotnet build src/OrderHub.Mcp
▸ src/OrderHub.Mcp/bin/Debug/net8.0/
OrderHub.Mcp.dll你的伺服器 OrderHub.Mcp.exe啟動器 OrderHub.Mcp.deps.json OrderHub.Mcp.runtimeconfig.json OrderHub.Core.dll複製進來 OrderHub.Infrastructure.dll複製進來 Microsoft.EntityFrameworkCore.SqlServer.dll ModelContextProtocol.dll …+ 約 40 個相依 dll

service 層是以「複本」形式打包進來。這個資料夾裡的 OrderHub.Core.dll 是哪個版本，伺服器就跑哪個版本——這就是為什麼「重新建置」才是把新規則搬到位的關鍵（見階段 04）。
02

部署 — 其實沒有伺服器可以部署

使用 stdio 傳輸（我們採用的方式）時，MCP 沒有 port、沒有 host、沒有雲端。bin/ 資料夾就是交付物。Claude Code 需要時直接啟動那支程式。

◆ 本機 · stdio  （本專案）

  • 交付物 = 磁碟上編譯好的 bin/ 資料夾
  • 以子程序啟動，只在 session 期間存活
  • 「重新部署」= 就是重啟這支程序
  • 需要自己的 DB 連線字串

◇ 遠端 · HTTP  （另一種選項）

  • 一支你自行架設、長時間執行的服務
  • 由多個 client 透過網路連線
  • 程式碼變更代表要明確地重建 + 重新部署
  • 重用 API 的驗證，而非直接存取 DB
03

training-repo/.mcp.json 裡不放程式碼、也不放工具。它只放一件事：名稱，以及「啟動這支程序」的確切指令。

04

一次程式碼變更如何傳到 agent

因為 .mcp.json 執行的是 dotnet run（先建置再啟動），每次啟動都會先重新建置——所以「重新啟動」會自動吃到 service 層的修改。但一支已經在跑的程序，會凍結在它啟動當下所載入的 DLL。

你改了 service 層，然後…會跑到新程式碼嗎？為什麼
開一個新的 Claude Code session（或在 /mcp 裡重新連線伺服器）會dotnet run 在啟動時重建 → 全新載入新版 OrderHub.Core.dll。
什麼都不做——維持同一個執行中的 session不會子程序仍在記憶體裡跑舊的 DLL。沒有熱重載（hot-reload），要重啟它。
設定指向預先建置好的 DLL，而非 dotnet run不會跑的是上次建置的結果——在你自己重建之前都是過期的。（這就是我們選 dotnet run 的原因。）
// 整條規則一句話 改規則 → 重啟伺服器 → 下次啟動執行 dotnet run = 重建 → agent 現在跑的就是新邏輯
!
變更後第一次啟動會比較慢（它正在編譯），過短的 client 連線逾時可能會錯過它。啟動 Claude Code 之前先跑一次 dotnet build，讓啟動時的建置變成「無動作」，伺服器就能瞬間連上。
一句話總結 — 建置 → bin 資料夾就是交付物 → Claude Code 每個 session 啟動它並透過 stdio 溝通 → 要吃到新程式碼就重啟。
